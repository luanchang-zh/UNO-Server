## 3. 本次完成：M6 Redis 快照与重启恢复

### 3.1 目标

让随机 token 和进行中牌局跨进程存活：服务重启后，客户端继续使用原 token 完成 WS 鉴权，RoomManager 从 Redis 重建成员、完整私有手牌、牌堆、行动阶段、MySQL `match_id` 和回合截止时间，并沿用 M4 的 Session 换绑流程继续游戏。

内存仍是运行期唯一可写真相；Redis 是崩溃恢复副本。单个快照写失败只记录错误，不回滚已经生效的玩法动作；配置了 Redis 但启动连接或全量扫描失败时拒绝监听，避免把可恢复房间静默当成空状态。

### 3.2 分层与依赖方向

```text
auth ──────→ store.SessionRepository ───┐
                                        ├─→ store/redis ─→ go-redis 连接池
room ──────→ store.RoomSnapshotRepository┘

room ──────→ uno.Engine.Snapshot / uno.Restore
game/uno ──→ 仍为无 IO 的纯规则引擎
```

Redis 仓储只理解 token 会话值和不透明房间 JSON；房间快照结构、版本校验和 Engine 恢复均留在 `internal/room` 与 `internal/game/uno`。进程入口只创建一个并发安全的 go-redis 客户端，让会话与快照共享连接池。

### 3.3 Redis 键与原子操作

| 键 | 值 | 生命周期 |
|----|----|----------|
| `uno:session:{token}` | `player_id`、昵称、绝对过期时间 JSON | 与 token 剩余 TTL 一致 |
| `uno:player_room:{player_id}` | `room_id` | 随活跃房间续期，离房时条件删除 |
| `uno:room:{room_id}` | 完整房间与 Engine JSON | 每个状态事件后续期 |
| `uno:room_index` | 活跃 `room_id` 集合 | 启动批量扫描；自动清理悬空成员 |

房间保存通过 Lua 在单 Redis 实例内原子执行 `SET PX`、`SADD` 与全部玩家索引更新。删除快照时会先比较 `player_room` 当前值，迟到的旧房清理不会误删玩家后来加入的新房间。本期部署边界仍为单进程、单 Redis 节点；以后切 Redis Cluster 时需统一哈希标签后再保留跨键脚本。

### 3.4 快照内容与写入边界

房间 JSON 包含 `schema_version`、单调 `revision`、`updated_at`、房间阶段、房主、稳定座位、连接/托管/连续超时状态、`turn_deadline`、`match_id` 和 `match_started_at`。进行中房间还嵌入 `uno.Snapshot`，覆盖 108 张实体牌归属、牌堆、弃牌堆、当前座位与颜色、罚牌池、摸牌决策、待选色动作、UNO 抓罚窗口及胜者候选。

| 触发 | Redis 行为 | 业务失败语义 |
|------|------------|--------------|
| 登录 | MySQL players 成功后写 token，再发布内存热缓存 | Redis 失败则登录失败，不返回半成品 token |
| 建房/加入/准备/开局 | mailbox 事件结束后同步写完整快照 | 房间动作保留，错误日志记录恢复副本落后 |
| 出牌/摸牌/选色/UNO/自动托管 | 每个成功或可能已改状态的命令后同步覆盖 | 不让 Redis 错误回滚权威 Engine |
| 断线/重连/离房 | 刷新成员状态；离房条件删除玩家索引 | 内存路由立即生效 |
| 终局/空房 | 删除房间、集合与仍指向本房的玩家索引 | MySQL 结算仍按 M5 事务边界处理 |
| 优雅退出 | 停止 HTTP 接入、关闭 WS，再向每间 mailbox 投递最终刷快照与停止命令 | 受统一 shutdown context 限制 |

### 3.5 启动恢复

1. 启动时先连接 MySQL 与 Redis，并执行 `PING`。
2. 通过 `uno:room_index` + `MGET` 按房间号稳定加载全部 JSON，同时清除缺少值的集合成员。
3. 校验房间 schema、修订号、成员唯一性、房主、阶段、座位顺序和 MySQL 对局元数据。
4. 调用 `uno.Restore` 再次校验阶段不变量、108 张牌守恒、待处理动作和终局结果。
5. 重建 Room 与 mailbox；全部 Session 指针清空、`connected=false`，进行中成员统一 `auto_play=true`。
6. 复用快照中尚未到期的回合截止时间；已到期时至少等待一次托管间隔。
7. 重建内存 `player→room` 路由并立即写回新的断线状态，随后才开始 HTTP 监听。
8. 单个损坏、版本不兼容、已经终局或玩家身份冲突的快照会被隔离并清理，不阻断其它合法房间恢复。

### 3.6 配置

| 环境变量 | 默认值 | 说明 |
|----------|--------|------|
| `UNO_REDIS_ADDR` | 空 | 为空时保持内存模式，非空时启用 Redis |
| `UNO_REDIS_USERNAME` / `UNO_REDIS_PASSWORD` | 空 | ACL 用户名与密码 |
| `UNO_REDIS_DB` | `0` | 单节点逻辑数据库编号 |
| `UNO_REDIS_POOL_SIZE` | `10` | 最大连接池大小 |
| `UNO_REDIS_MIN_IDLE_CONNS` | `1` | 最小空闲连接数 |
| `UNO_REDIS_DIAL_TIMEOUT` | `3s` | 建连超时 |
| `UNO_REDIS_READ_TIMEOUT` / `UNO_REDIS_WRITE_TIMEOUT` | `2s` | 命令读写超时 |
| `UNO_REDIS_OPERATION_TIMEOUT` | `2s` | 登录、快照、恢复的业务超时 |
| `UNO_REDIS_ROOM_SNAPSHOT_TTL` | `2h` | 活跃房间与玩家索引兜底 TTL |

### 3.7 验收结果

- [x] token 写入 Redis 后才发布内存缓存；新 Service 实例可用原 token 回源鉴权
- [x] token TTL 到期自动失效，过期热缓存会同步清理
- [x] Lua 保存/删除覆盖快照、room_index、player_room 和迟到清理保护
- [x] waiting 与 playing 房间均可恢复；进行中 Engine 快照逐字段保持一致
- [x] 损坏快照被隔离清理，Redis 全量加载失败会阻止启动
- [x] 真实 WebSocket 集成测试完成“原 token 重连、恢复原私有手牌、继续行动”
- [x] Redis 使用内存服务器测试，无需依赖本机 Docker 服务
- [x] 新增函数与复杂边界使用中文注释

## 5. 编码与质量约定（全程）

| 项 | 要求 |
|----|------|
| 注释 | 非测试 Go 代码函数级注释；复杂逻辑块级/行级 |
