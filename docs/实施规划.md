## 3. 本次完成：M5 MySQL 三表持久化

### 3.1 目标

把玩家身份、对局元数据和终局结果写入 MySQL，同时保持普通出牌、摸牌、选色和托管行动只修改 Room 与 Engine 内存状态。数据库故障不得发布半成功登录或半成品牌局，终局元数据与所有玩家结果必须原子提交。

### 3.2 分层与依赖方向

```text
auth ──────→ store.PlayerRepository ──┐
                                      ├─→ store/mysql ─→ database/sql
room ──────→ store.MatchRepository ───┘

game/uno ──→ 仍为无 IO 的纯规则引擎
```

业务层只依赖 `internal/store` 中的小接口，MySQL 驱动和 SQL 语句不会反向渗入 auth、room 或 game。进程入口创建并复用一个 `sql.DB` 连接池，关闭进程时统一释放。

### 3.3 主键与连接配置

业务主键延续原有 `BIGINT` 表结构，采用 41 位毫秒时间、10 位节点号、12 位毫秒内序列号。玩家、对局和结果共享同一个线程安全生成器；多实例部署时必须为每个实例配置不同的 `UNO_NODE_ID`。

| 环境变量 | 默认值 | 说明 |
|----------|--------|------|
| `UNO_NODE_ID` | `1` | 雪花节点号，范围 0–1023 |
| `UNO_MYSQL_DSN` | 空 | 为空时保持纯内存模式，非空时启用 MySQL |
| `UNO_MYSQL_MAX_OPEN_CONNS` | `10` | 最大打开连接数 |
| `UNO_MYSQL_MAX_IDLE_CONNS` | `5` | 最大空闲连接数 |
| `UNO_MYSQL_CONN_MAX_LIFETIME` | `3m` | 单连接最长复用时间 |
| `UNO_MYSQL_CONN_MAX_IDLE_TIME` | `1m` | 空闲连接最长保留时间 |
| `UNO_MYSQL_OPERATION_TIMEOUT` | `3s` | 单次连接、迁移或业务写入超时 |
| `UNO_MYSQL_AUTO_MIGRATE` | `true` | 启动时幂等创建三张表 |

Repository 会强制开启 `parseTime`、UTC 会话时区和 `utf8mb4_unicode_ci` 连接排序规则，避免 DSN 漏配造成时间或中文字段语义漂移。

### 3.4 写入边界

| 边界 | MySQL 行为 | 失败语义 |
|------|------------|----------|
| 游客登录 | insert `players` | 不发布 token 和内存会话，HTTP 返回失败 |
| 房主开局 | insert `matches(status=playing)` | Engine 不挂载，房间保持 waiting，可重试 |
| 普通回合 | 无 SQL | 热路径始终纯内存 |
| 终局 | update `matches` + insert 全部 `match_results` | 单事务回滚；终局视图仍以权威 Engine 为准并记录错误 |

结算实体直接从 `uno.RoundResult.Players` 的稳定座位顺序生成，保存胜者得分、各玩家剩余手牌分值和张数。仓储会在开启事务前再次校验结果数量、座位、胜者与 match_id 一致性。

### 3.5 MySQL 实现约束

- 使用 `github.com/go-sql-driver/mysql` 与标准库 `database/sql`，不引入 ORM。
- 连接启动即 `PingContext`，不可达时拒绝启动持久化模式。
- 三张表使用 `CREATE TABLE IF NOT EXISTS` 幂等创建；可通过配置关闭自动建表。
- SQL 值全部使用占位参数，不拼接玩家输入。
- 结算使用 `BeginTx`、事务内 `UPDATE`/预编译 `INSERT`、`Commit`；任一错误通过延迟 `Rollback` 回收。
- `sql.DB` 只创建一次并设置连接数、空闲时间和连接寿命上限。

### 3.6 验收结果

- [x] 玩家写入成功后才发布 token；失败不会产生半成功会话
- [x] 开局记录失败时房间保持 waiting，Engine 不对外发布
- [x] 完整一局生成一条 match 和按座位对齐的全部 results
- [x] 结算任一 SQL 失败会回滚整个事务
- [x] 雪花 ID 并发生成 8000 个主键无重复，并拒绝时钟回拨
- [x] 完整一局持久化与开局失败端到端路径连续执行 20 次通过

### 3.7 后续边界

M5 只保存冷数据，token、玩家到房间的映射、手牌和进行中 Engine 仍在单进程内存。下一阶段 M6 将接入 Redis 会话与房间快照，保存 match_id，并在进程重启后恢复全员断线托管的牌局。

## 4. 后续阶段摘要

### M1 房间（已完成）

| 交付 | 要点 |
|------|------|
| RoomManager | roomId → Room |
| Room mailbox | 单协程串行 |
| 消息 | create_room / join_room / leave / ready / start（仅校验人数与准备，可暂不真正开牌） |
| 广播 | 成员列表、准备状态 |
| 日志 | 每条房间相关 WS 消息一条 |

**验收：** 2～3 客户端同房状态一致。

### M2 规则引擎（已完成）

| 交付 | 要点 |
|------|------|
| `internal/game/uno` | 牌堆、合法性、叠罚、Reverse/Skip、结算 |
| 单测 | 表驱动覆盖主路径与边界 |
| 无 IO | 不依赖 session/room/store |

**验收：** `go test ./internal/game/uno/...` 绿。

### M3 联调一局（已完成）

Room 开局创建 Engine；出牌/摸牌/选色/UNO；私有手牌 vs 公开桌面；非法操作拒绝。  
**验收：** 2 人手打完一局。

### M4 超时与重连（内存，已完成）

回合定时器事件进 mailbox；断线占座 + 托管；重连全量快照。  
**验收：** 拔线再连能续打。

### M5 MySQL（已完成）

`players` / `matches` / `match_results`；登录写 players；开局/结算写库。  
**验收：** 局后库中有记录。

### M6 Redis 重启（下一步）

token 会话；房间快照；启动加载；优雅退出刷盘。  
**验收：** kill -9 后拉起，原 token 重连续打。

### M7 打磨

空房回收、指标可选、日志字段统一、README 使用说明。

## 5. 编码与质量约定（全程）

| 项 | 要求 |
|----|------|
| 注释 | 非测试 Go 代码函数级注释；复杂逻辑块级/行级 |
| 日志 | 仅边界打点（HTTP 中间件 / WS 消息结束）；`WithContext` |
| 错误 | `errors.Is` / `fmt.Errorf("%w")` |
| 依赖方向 | `session/room → game`；`game` 不依赖网络与 DB |
| 单文件 | 尽量 < 500 行，函数 < 50 行 |
| 测试 | 新公共能力尽量有单测；规则包覆盖优先 |

## 6. 风险与顺序纪律

| 风险 | 规避 |
|------|------|
| 过早上房间+规则 | 先 M0-b 管道再 M1 再 M2 |
| 出牌写 DB | 禁止；仅结算写 MySQL |
| 在 Room 协程里直接 Write WS | 只投递 session.send |
| 无 trace 刷屏日志 | 中间路径不打访问日志 |
