## 3. 本次完成：M3 房间挂接规则引擎

### 3.1 目标

房主开局时按房间座位创建 `uno.Engine`；所有玩法命令继续进入 Room mailbox 串行执行；每次成功变更后向各玩家发送独立的安全视图，直至产生终局结算。

### 3.2 玩法协议

所有消息继续使用统一 Envelope。客户端玩法命令如下：

| type | payload | 说明 |
|------|---------|------|
| `play_card` | `{ "card_id", "say_uno" }` | 打出实体牌，可同时喊 UNO |
| `draw_card` | 空 | 普通摸一张，或接受全部累计罚牌 |
| `pass` | 空 | 保留刚摸到的可出牌并结束回合 |
| `choose_color` | `{ "color" }` | 万能牌选择 red/yellow/green/blue |
| `call_uno` | 空 | 在窗口内主动补喊 UNO |
| `catch_uno` | `{ "player_id" }` | 抓罚漏喊 UNO 的目标玩家 |

服务端使用 `game_state` 下发 `uno.View`。该视图包含公共桌面、各玩家手牌数量，以及接收者自己的完整手牌和可出牌提示；不发送其他玩家手牌。

### 3.3 运行链路

```
Client game command
  → Session.readPump
  → RoomManager.Route
  → Room.mailbox
  → uno.Engine 校验并修改状态
  → 为每名成员调用 ViewFor(playerID)
  → Session.send
  → Client game_state
```

房间仍是唯一写者；规则引擎不依赖 Session、Room 或数据库。非法命令只返回带原 `request_id` 的 `error`，不广播新状态。

### 3.4 终局与隐私

- Engine 进入 `finished` 后，房间同步切换到 `settled`。
- 终局 `game_state` 向所有成员公开同一份结算结果。
- `Hand`、`DrawnCardID` 和当前玩家的 `PlayableCardIDs` 始终按接收者生成。
- 每次广播使用完整视图，M4 重连时可以直接复用同一数据结构。

### 3.5 验收结果

- [x] 房主 `start` 后创建并挂载 Engine
- [x] 出牌、摸牌、过牌、选色、补喊 UNO、抓 UNO 均可经 WS 路由
- [x] 非当前玩家操作返回稳定错误码且不改变状态
- [x] 双方公共状态一致，私有手牌不互相泄漏
- [x] 两个真实 WebSocket 客户端可自动完成一整局并获得一致结算
- [x] 完整一局随机牌序连续执行 20 次通过
- [x] `go test ./...` 与 `go vet ./...` 通过

### 3.6 后续边界

M3 假设玩家在一局内保持连接。回合定时器、断线占座、自动托管和 Session 换绑统一留到 M4，避免在房间挂接规则时同时引入生命周期状态。

## 4. 后续阶段摘要

### M1 房间（已完成）

| 交付 | 要点 |
|------|------|
| RoomManager | roomId → Room |
| Room mailbox | 单协程串行 |
| 消息 | create_room / join_room / leave / ready / start（仅校验人数与准备，可暂不真正开牌） |
| 广播 | 成员列表、准备状态 |
| 日志 | 每条房间相关 WS 消息一条 |

**验收：** 2～3 客户端同房状态一致。

### M2 规则引擎（已完成）

| 交付 | 要点 |
|------|------|
| `internal/game/uno` | 牌堆、合法性、叠罚、Reverse/Skip、结算 |
| 单测 | 表驱动覆盖主路径与边界 |
| 无 IO | 不依赖 session/room/store |

**验收：** `go test ./internal/game/uno/...` 绿。

### M3 联调一局（已完成）

Room 开局创建 Engine；出牌/摸牌/选色/UNO；私有手牌 vs 公开桌面；非法操作拒绝。  
**验收：** 2 人手打完一局。

### M4 超时与重连（内存，下一步）

回合定时器事件进 mailbox；断线占座 + 托管；重连全量快照。  
**验收：** 拔线再连能续打。

### M5 MySQL

`players` / `matches` / `match_results`；登录写 players；开局/结算写库。  
**验收：** 局后库中有记录。

### M6 Redis 重启

token 会话；房间快照；启动加载；优雅退出刷盘。  
**验收：** kill -9 后拉起，原 token 重连续打。

### M7 打磨

空房回收、指标可选、日志字段统一、README 使用说明。

## 5. 编码与质量约定（全程）

| 项 | 要求 |
|----|------|
| 注释 | 非测试 Go 代码函数级注释；复杂逻辑块级/行级 |
| 日志 | 仅边界打点（HTTP 中间件 / WS 消息结束）；`WithContext` |
| 错误 | `errors.Is` / `fmt.Errorf("%w")` |
| 依赖方向 | `session/room → game`；`game` 不依赖网络与 DB |
| 单文件 | 尽量 < 500 行，函数 < 50 行 |
| 测试 | 新公共能力尽量有单测；规则包覆盖优先 |

## 6. 风险与顺序纪律

| 风险 | 规避 |
|------|------|
| 过早上房间+规则 | 先 M0-b 管道再 M1 再 M2 |
| 出牌写 DB | 禁止；仅结算写 MySQL |
| 在 Room 协程里直接 Write WS | 只投递 session.send |
| 无 trace 刷屏日志 | 中间路径不打访问日志 |
