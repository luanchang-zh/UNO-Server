# UNO Server 技术方案

> 对应功能需求：`docs/功能需求.md`  
> 目标：可落地的整体架构，覆盖 **WS 实时对局、玩家重连、进程重启恢复、MySQL 持久化**。  
> 原则：热路径纯内存；落库异步/低频；房间串行化；服务端权威。

**状态：** 草案（可随实现微调，核心边界尽量不改）  
**最后更新：** 2026-08-03

---

## 1. 目标与边界

### 1.1 要练到的能力

| 能力 | 说明 |
|------|------|
| 实时房间服 | WebSocket + 房间状态机 + 广播 |
| 玩家重连 | 同进程断线：token 找回座位 + 状态快照下发 |
| 进程重启 | 重启后恢复「进行中房间/牌局」，玩家可再连上继续 |
| 持久化 | MySQL：玩家、对局记录、对局结果 |

### 1.2 明确不做（控制复杂度）

- 多机房、跨服匹配、服务网格  
- 出牌逐步写 MySQL  
- 完整回放系统、反外挂体系  
- 分库分表、读写分离  

### 1.3 部署形态（本期）

**单进程单实例** 即可覆盖上述学习目标。  
「进程重启」= 本机挂掉再拉起后，从 **Redis 房间快照 + MySQL 冷数据** 恢复；不做多节点房间迁移。

## 2. 总体架构

```
                    ┌─────────────────────────────────────────┐
  Client            │              UNO Server (单进程)          │
                    │                                         │
  HTTP ────────────►│  Auth / Health / (可选管理接口)            │
  (登录拿 token)     │                                         │
                    │  SessionManager                          │
  WebSocket ───────►│   ├─ 每连接 readPump + writePump         │
  (创建/加入/对局)   │   └─ send chan 出站缓冲                   │
                    │              │                          │
                    │              ▼                          │
                    │  RoomManager ──创建/查找/销毁房间         │
                    │              │                          │
                    │       ┌──────┴──────┐                   │
                    │       ▼             ▼                   │
                    │    Room loop     Room loop              │
                    │    (mailbox)     (mailbox)              │
                    │       │             │                   │
                    │       └──────┬──────┘                   │
                    │              ▼                          │
                    │         uno.Engine（纯规则，可单测）       │
                    └───────┬─────────────────┬───────────────┘
                            │                 │
                   异步写    ▼                 ▼  快照读写
                      ┌──────────┐       ┌──────────┐
                      │  MySQL   │       │  Redis   │
                      │ 冷数据   │       │ 热快照   │
                      └──────────┘       └──────────┘
```

### 2.1 通道划分（已确认）

| 通道 | 职责 |
|------|------|
| **HTTP** | 游客登录（发 `playerId` + `token`）、健康检查、后续可选管理接口 |
| **WebSocket** | 创建/加入/离开房间、准备、开局、出牌/摸牌/选色、UNO、重连绑定后的全部实时交互 |

### 2.2 逻辑分层

| 层 | 包建议 | 职责 |
|----|--------|------|
| 接入 | `cmd/server`, `internal/server` | 监听、路由、优雅退出 |
| 会话 | `internal/session` | WS 生命周期、鉴权、读写泵、出站队列 |
| 协议 | `internal/protocol` | 消息类型、编解码、错误码 |
| 房间 | `internal/room` | 房间生命周期、mailbox、广播、托管/超时事件 |
| 玩法 | `internal/game/uno` | 纯内存规则引擎，无 IO |
| 持久化 | `internal/store` | MySQL Repository + Redis Snapshot |
| 配置/日志 | `internal/config` | 环境变量、slog |

**依赖方向：** `session/room → game`；`room → store`（仅结算与快照，不反向）。  
`uno.Engine` **禁止** 依赖网络与数据库。

## 3. 并发与运行时模型

### 3.1 连接（Session）

每个已建立的 WebSocket：

| 资源 | 说明 |
|------|------|
| 1 × 连接 | `gorilla/websocket` 或等价 |
| 1 × `readPump` goroutine | 读消息 → 解析 → 投递事件 |
| 1 × `writePump` goroutine | 消费 `send chan` → 写连接 |
| 1 × `send chan` | 有界缓冲（如 64）；满则按策略断开或丢弃非关键 |

**禁止** 在 `readPump` 里直接改房间/牌局状态。

### 3.2 房间（Room Actor）

| 资源 | 说明 |
|------|------|
| 1 × mailbox `chan Event` | 所有进房事件唯一入口 |
| 1 × loop goroutine | 串行 `Handle(event)`，房间状态唯一写者 |
| 内存状态 | 成员、准备、阶段、绑定的 `Engine`、托管标记等 |

事件来源示例：

- 玩家消息（出牌、准备…）  
- 断线 / 重连绑定  
- 回合超时（定时器回调 **只投递事件**，不直接改状态）  
- 快照定时触发（可选）  
- 优雅停机：`Drain/Snapshot` 事件  

### 3.3 RoomManager

- 维护 `roomId → *Room`  
- 创建房间、按房间号加入路由  
- 可用 `sync.RWMutex` 保护 map（访问频率低，无需再套一层 actor）  
- 空房超时销毁；销毁前删 Redis 快照  

### 3.4 数据流（出牌一例）

```
Client play_card
  → readPump
  → Room.mailbox
  → Room.Handle → Engine.Play
  → 组装 S2C（公开桌面 / 私有手牌）
  → 各 Session.send
  → writePump → Client
  →（异步）若需：更新 Redis 快照 / 局终写 MySQL
```

## 4. 身份、登录与 Token

### 4.1 登录（HTTP）

`POST /api/v1/auth/guest`（名称可调）

- 入参：可选 `nickname`  
- 出参：`player_id`, `token`, `expires_at`  
- 服务端：写入/更新 MySQL `players`；token 建议 **JWT** 或 **随机串 + Redis/内存会话表**  

练手推荐：**随机 `token` + Redis 存 `token → player_id`（TTL）**，重启后 token 仍可用（见第 6 节）。  
若 token 只放内存，进程重启后所有人要重新登录（可接受为降级，但与「重启续玩」冲突，故 token 放 Redis）。

### 4.2 WS 握手鉴权

- URL：`/ws?token=...` 或首包 `auth`  
- 校验通过后绑定 `Session.PlayerID`  
- 若该玩家有「可重连座位」，走重连流程（第 5 节），否则视为大厅连接

## 5. 玩家重连（同进程 + 跨重启统一协议）

### 5.1 概念

| 概念 | 含义 |
|------|------|
| `player_id` | 长期身份，进 MySQL |
| `conn_id` | 单次 WS 连接 ID，断线即失效 |
| 座位绑定 | 房间内 `seat → player_id`，对局中**不因断线丢座位** |
| 重连 | 新 `conn_id` 证明是同一 `player_id`，挂回原座位 |

### 5.2 断线时（Room 处理 Disconnect）

1. 标记该座位 `connected=false`  
2. **不**立刻移除座位（对局中）  
3. 进入/保持 **托管**（按需求：超时与托管规则）  
4. 通知房内其他人：该玩家断线并进入托管
5. M6 接入 Redis 后立即刷新房间快照

### 5.3 重连时

1. WS 鉴权通过  
2. 查「该 player 是否在某房间占座」：  
   - 内存 RoomManager 优先  
   - 若进程刚恢复：先从 Redis 加载房间再查  
3. 绑定新 Session 到该座位，`connected=true`，可取消纯托管（若产品定义为重连后恢复手动）  
4. 下发 **全量快照**（非增量）：  
   - 公开：房间阶段、成员、顶牌、颜色、方向、轮次、手牌张数、惩罚池…  
   - 私有：自己手牌  
   - 生命周期：成员的 `connected`、`auto_play`、`timeout_strikes`，以及 `turn_deadline`
5. 之后消息流与正常连接相同  

### 5.4 重连窗口

- 对局中：直到本局结束都可重连（与「托管打完」一致）  
- 局结束后：座位可清理；是否允许回房间旁观本期不做  
- 等待阶段断线：当前版本立即按离开处理；后续如需候场恢复再增加短 TTL

## 6. 进程重启恢复

仅靠 MySQL 的「玩家/对局/结果」**不够**恢复进行中的手牌——那些是冷数据。  
重启续玩依赖 **热快照（Redis）**。

### 6.1 职责划分

| 存储 | 职责 |
|------|------|
| **内存** | 运行时唯一可写真相（Room 协程内） |
| **Redis** | 进行中房间/牌局快照、token 会话、可选 `player→room` 索引 |
| **MySQL** | 玩家档案、对局元数据、结算结果（长期） |

### 6.2 快照内容（Redis）

Key 设计示例：

```
uno:session:{token}          → player_id, expire
uno:player_room:{player_id}  → room_id          # 重连路由
uno:room:{room_id}           → JSON 快照
uno:room_index               → SET of room_id   # 启动扫描（或 SCAN 前缀）
```

房间快照 JSON 建议包含：

- 房间：id、阶段、人数上限、房主、座位列表（player_id、nickname、ready、connected、托管）  
- 牌局（若 playing）：完整 Engine 可序列化状态  
  - 牌库、弃牌堆、各手牌、当前玩家、方向、当前颜色、pendingDraw、UNO 可质疑状态等  
- 版本号 / `updated_at`，防止旧快照覆盖新状态  

### 6.3 何时写 Redis 快照

| 触发 | 策略 |
|------|------|
| 进房/离房/准备/开局 | 立即写 |
| 每次出牌/摸牌/选色等牌局变更 | 立即写 **或** 合并为「每 N ms 最多一次」（防抖）；练手可先 **每关键事件立即写** |
| 断线/重连 | 立即写 |
| 定时 | 每 5–10s 兜底写一次（防漏） |
| 房间销毁/局终 | 删除快照；局终同时异步写 MySQL |

**注意：** 快照失败不应阻断出牌（记录错误日志）；接受极端情况下重启丢最新几步的风险，或同步写快照（更简单、略增延迟）。练手建议：**mailbox 内同步写 Redis，逻辑简单**。

### 6.4 进程启动恢复流程

```
1. 连接 MySQL / Redis
2. SCAN/读取所有 uno:room:* 快照
3. 反序列化 → 重建 Room + Engine，启动 mailbox loop
4. 所有座位 connected=false，统一托管，直到玩家 WS 重连
5. 恢复回合超时定时器（按快照中的 deadline 或重新给一轮时限）
6. 开始接受新连接与重连
```

### 6.5 优雅退出

收到 SIGTERM：

1. 停止接受新连接  
2. 向所有 Room 发送 `Shutdown`：刷最终快照  
3. 关闭 WS  
4. 退出  

保证「杀进程」与「kill -9」的差异：后者只靠定时/事件快照兜底。

### 6.6 与 MySQL 对局记录的关系

| 阶段 | MySQL | Redis |
|------|-------|-------|
| 等待中房间 | 可不写 | 有快照即可 |
| 开局 | insert `matches`（status=playing） | 快照含 match_id |
| 对局中 | 不更新每步 | 持续快照 |
| 结算 | update match + insert results | 删房间快照 |
| 异常重启 | match 仍为 playing | 从快照恢复继续；最终结算时再 update |

## 7. MySQL 表设计

> 字符集 `utf8mb4`；时间用 `UTC` 的 `DATETIME(3)` 或 `TIMESTAMP`。  
> 主键：当前实现统一使用 `BIGINT` 雪花 ID；41 位毫秒时间 + 10 位节点号 + 12 位序列号。

### 7.1 `players` 玩家

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK | `player_id` |
| `nickname` | VARCHAR(32) | 展示名，允许重名 |
| `created_at` | DATETIME(3) | 首次创建 |
| `updated_at` | DATETIME(3) | 资料更新 |
| `last_login_at` | DATETIME(3) | 最近登录 |

索引：无强制唯一昵称。  
写入时机：首次游客登录 insert；改昵称/登录 update。

### 7.2 `matches` 对局记录

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK | `match_id` |
| `room_id` | VARCHAR(16) | 业务房间号（便于排查） |
| `status` | TINYINT/VARCHAR | `playing` / `finished` / `aborted` |
| `player_count` | TINYINT | 开局人数 2–6 |
| `winner_player_id` | BIGINT NULL | 胜者；中止可空 |
| `started_at` | DATETIME(3) | 开局时间 |
| `ended_at` | DATETIME(3) NULL | 结束时间 |
| `created_at` | DATETIME(3) | 行创建 |

索引：`idx_room_id (room_id)`，`idx_started_at (started_at)`。  
写入时机：开局 insert；结算/异常终止 update。

### 7.3 `match_results` 对局结果（每局每玩家一行）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK | 代理主键 |
| `match_id` | BIGINT | 关联 `matches.id` |
| `player_id` | BIGINT | 玩家 |
| `seat_index` | TINYINT | 座位 0–5 |
| `is_winner` | TINYINT(1) | 是否胜者 |
| `score` | INT | 本局得分（胜者=其余手牌点之和，负者可为 0 或负分策略二选一；**建议：胜者记正分，其他人记 0**） |
| `hand_points` | INT | 结束时该玩家手牌点数（计分用） |
| `cards_left` | TINYINT | 剩余手牌张数 |
| `created_at` | DATETIME(3) | |

索引：`UNIQUE(match_id, player_id)`，`idx_player_id (player_id)`。  
写入时机：**仅结算时**批量 insert（事务内与 update `matches` 一起）。

### 7.4 表关系

```
players 1 ─── N match_results N ─── 1 matches
```

### 7.5 不进 MySQL 的数据

- 手牌明细、出牌序列（除非以后做回放）  
- 心跳、准备瞬时状态  
- token 明文（可只存 Redis）

| 类别 | 选型 | 说明 |
|------|------|------|
| 语言 | Go 1.25 | 已有 module |

**依赖保持精简：** WS + MySQL driver + Redis client + 可选 uuid。

## 10. 核心流程串联

### 10.1 登录 → 建房 → 开局 → 结算

```
HTTP guest login → MySQL players insert → token 进 Redis
WS connect(token)
WS create_room → RoomManager 建房 → Redis 快照
WS join_room → 进房 → 快照
WS ready / start → 开局 → MySQL matches insert → Engine 发牌 → 快照
… 出牌循环（内存 + 快照）…
有人胜 → Engine 结算 → MySQL 事务写 results + update match → 删 Redis 房间快照
→ 房间回 waiting 或销毁
```

### 10.2 断线重连

```
disconnect → 座位保留 + 托管 → 快照
新 WS + 同 token → 查 player_room → 绑定座位 → 下发全量快照 → 恢复操作
```

### 10.3 进程崩溃再拉起

```
start → 加载 Redis 所有 room 快照 → 重建 Room（全员断线托管）
玩家用原 token 重连 → 同 10.2
打完 → MySQL 结算
```

## 11. 实现里程碑（建议顺序）

| 阶段 | 交付 | 验收 |
|------|------|------|
| **M0** | HTTP health + 游客登录 + WS 连通 + ping/pong | 能连上、鉴权失败断开 |
| **M1** | RoomManager + 创建/加入/准备/广播（无牌） | 多客户端房间状态一致 |
| **M2** | `uno.Engine` + 单测（含叠罚） | 纯逻辑测通关键规则 |
| **M3** | 房间挂引擎，完整一局 + 非法操作拒绝 | 能打完一局 |
| **M4** | 超时托管 + 断线重连（内存） | 拔线再连恢复手牌 |
| **M5** ✅ | MySQL 三表 + 登录/开局写入 + 事务结算 | SQL 测试与完整一局持久化通过 |
| **M6** | Redis 快照 + 启动恢复 | kill 进程再起，重连续打 |
| **M7** | 优雅退出、指标/日志打磨 | 可长期挂着玩 |

## 12. 风险与对策

| 风险 | 对策 |
|------|------|
| 快照太大/太频拖慢出牌 | 先同步写；若延迟明显再改为「状态 version + 防抖」 |
| Redis 与内存不一致 | 运行时以内存为准；Redis 仅恢复用；局终删 key |
| 结算写库失败 | 重试队列 + 日志；可先打本地文件补偿（练手：重试 3 次打错误日志） |
| 写泵阻塞拖死房间 | 有界 `send`，满则踢连接，Room 不因 Write 阻塞 |
| 序列化与版本不兼容 | 快照带 `schema_version`，不兼容则丢弃房间并 abort match |

## 14. 题外：大型游戏服如何保证「体验稳定性」

> 非本项目实现范围，供对照学习。稳定性 ≈ **延迟可预期 + 少掉线 + 少不同步 + 故障可恢复**。

### 14.1 体验稳定性通常指什么

| 维度 | 玩家体感 | 服务端手段 |
|------|----------|------------|
| 延迟 | 操作「跟手」 | 同区域部署、短路径、热逻辑纯内存、避免热路径 IO |
| 流畅 | 不卡顿、少抖动 | 限帧/合并广播、写缓冲、背压、避免全局锁 |
| 公平/正确 | 不「明明出了却无效」 | 服务端权威、帧/序号、房间串行或确定性模拟 |
| 在线连续 | 断线可续、切换网络可回 | 重连、状态快照、会话迁移 |
| 高可用 | 服务器挂了还能玩 | 多实例、房间热备/迁移、有状态分片、快速拉起 |
| 可运营 | 卡顿能定位 | 指标、日志、追踪、压测、故障演练 |

### 14.2 架构层面常见做法

1. **分区与分片**  
   - 网关无状态；房间/场景有状态。  
   - 按 `room_id` / `map_id` 一致性哈希到某节点，避免乱飞。  

2. **有状态服务的容灾**  
   - 房间主备、或快照 + 快速重建（类似本方案 Redis 快照放大版）。  
   - 节点下线时 **迁移房间** 到其他机（迁移窗口内可能短暂只读/暂停）。  

3. **网关层**  
   - 统一接入、限流、防刷、TLS、多协议；后端挂了可踢到维护页而非假死。  

4. **热路径工程纪律**  
   - 出牌/移动：**零同步 DB**；落库异步。  
   - 对象池、预分配、少 GC 抖动（部分用 C++/自研引擎）。  
   - 关键路径 CPU 亲和、隔离吵闹邻居。  

5. **时间与同步模型**  
   - 回合制（UNO）：房间串行即可，天然好做稳。  
   - 强实时动作：定帧服务器、客户端预测 + 和解、延迟补偿。  

6. **降级与过载保护**  
   - 队列满拒绝进房、只读旁观、关非核心系统（聊天/好友）。  
   - 保护核心：匹配进房、移动/出牌通道优先。  

7. **可观测与发布**  
   - 延迟分位（P50/P99）、房间数、消息堆积、掉线率、重连成功率。  
   - 金丝雀、分区分批发布；配置热更新；一键回滚。  

8. **客户端协同**  
   - 本地预测、断线提示、自动重连、弱网策略；体验稳定性是 **端云一体**，不单靠服务器。  

### 14.3 和本练手项目的映射

| 大厂做法 | 本项目对应练法 |
|----------|----------------|
| 服务端权威 | `uno.Engine` 只信服务端 |
| 有状态房间 | Room mailbox 串行 |
| 热路径无 DB | 出牌只改内存 |
| 断线重连 | Session 换绑 + 全量快照 |
| 进程容灾 | Redis 房间快照 + 启动恢复 |
| 冷数据沉淀 | MySQL 三表 |
| 过载保护 | 有界 channel、满则踢 |
| 可观测 | slog 关键路径日志；后续可加 Prometheus |

**一句话：** 大厂靠「热状态内存化 + 分片容灾 + 异步落库 + 重连/迁移 + 过载降级 + 全链路观测」把体验做稳；你用 **单机版的同一思想** 就能练到主干。
